## Legend

- **Blocks:** the four outcomes the task defines.
  - (1) a snap, or a drive being staged or played;
  - (2) a hand-off, sending or applying a drive-end outcome;
  - (3) the 1 PT / 2 PT modal or the try;
  - (4) the final / stats screen.
- **Risk:**
  - **U** = UNBOUNDED: no clear site, or the only clear site is on a path that can be skipped (an early return, a catch, or the callback of a promise that may never settle). Listed separately below the table.
  - **H** = high, **M** = medium, **L** = low (bounded by its own timer or tick count).
- **Proposed** gives a maximum lifetime, then the expiry action (→). Every expiry action obeys the owner's rules:
  - it awards no points;
  - it never rewinds the clock within a quarter;
  - it never takes the ball from a hidden or away player (it shows the honest status instead);
  - it never ends the game early.
- "Screen-on" means counted only while `document.hidden` is false.

| `_rb2p_quarterResumePending` | No time bound. It clears only on a snap, a clock tick, a send, an apply, a void, or the Q3 law. |
| `_rb2p_gameOverReported` | Latched before the report renders. `renderFinal()` (13901) is not inside a try, and nothing retries. The latch then stops every detector (12764, 13514, 13966). |

| `rb2p_skipResumeOnce` (sessionStorage) | Consumed only at 16380, after about 10 awaits inside `tryRestore`. The catch-all (16510–16513) skips it. |
| `_rb2p_q3LawApplied` | Set to true (13222) before B's forced drive runs. A refused force (for example `p6ScorerOwes`) is never retried. |
| `_rb2p_p6AwaitDriveMs` | Re-arms itself every 4 s (428) with no maximum count. It is cleared only by a real running drive or by the two retire conditions. |
| `pollR` resume loop (5365) | While in the match room, a failing force retries every 50 ms with no maximum (5420). The `triesR > 2400` bound covers only the not-in-match branches (5368, 5370). |

## C. Top 10 riskiest

1. **`window._twoPlayer.pending` (row 1).** A generic hand-off that lands while this phone thinks it is live sits in memory with no expiry. It has already been acked (17418–17428), so a reload loses it and the resume insurance skips it (16337). While it sits there the field check is blind (18118). This is a lost hand-off whose sender believes it was delivered.
2. **`outcomePollBusy` (row 2).** A single REST GET that never answers disables the REST receive path for good. That path is exactly the MSZT fallback for a half-open SDK socket. The audit flush already has the right pattern (10 s in-flight cap at 221 plus AbortController at 236); this poll does not.
3. **`_fbTokInFlight` (row 3).** A V419 addition. If a token refresh hangs (a stalled TCP connection on school Wi-Fi), every REST path waits on it. That covers the REST send fallback, the delivery re-send, the poll, the held/ack patches, the p6 ledger and the heartbeat, which also makes the partner's honest status go stale. It only bites at refresh time, but it has no bound when it does.
4. **`patOwed()` drop (row 4).** While any S1–S5 signal is up, even a stale one inside its 35 s wall, a real generic hand-off is consumed and never applied (11286–11296). The wall later releases the conversion but does not bring the hand-off back. Both phones end up parked, and a guessing recovery follows.
5. **`userOutcomeSendInProgress` (row 5).** This caused the known 5.5-minute freeze (VJGW). No time bound; it is safe only because every current `waiting = false` writer clears it by convention. Its reset inside `forceUserOffenseDrive` sits after two refusal returns. When it is stuck it swallows every hand-off (6140), mutes the dead-stage watchdog (7593) and mutes the empty-field law (2971).
6. **OT coin flip, request and apply (rows 6–7).** The flip is single-writer (host only), SDK only, requested once per period with errors swallowed, and consumed before it is applied (`applyOtKickoff` can return without applying at 13341). Any one failure leaves both phones parked at the start of OT, with nothing left to retry.
7. **Final record and latch (rows 8–9).** `gameOverReported` latches before the render, and `renderFinal` (13901) is not in a try. The partner's stats screen depends on an SDK-only write and an SDK-only read (13904 / 16953). A waiting partner cannot reach its own final because V293 floors its clock at 0:01. So a half-open socket at the horn means one phone never gets the stats screen.
8. **OT end counters (row 10).** Overtime has no end bound, and the equal-possession counts move on different paths on the two phones. Parks count on the parking phone; restores and rescues do not count on the other. Once the counts diverge, round-end may never be true on both phones, and nothing reconciles them.
9. **`_rb2p_quarterResumePending` (row 11).** No time bound. While it is set on a dead stage, the drive-end watchdog keeps choosing a keep, or a refused keep, over a hand-off (7631–7745). It relies on a snap happening to clear it.
10. **`rb_room` deleted by `tryRestore`'s catch-all (row 12).** Any one rejected read on a flaky network permanently turns a reload into "not in a game". Resume is supposed to be a first-class path (Phase 2 property 4). The same catch also strands `rb2p_skipResumeOnce` (row 13).

Just outside the top 10:

- **Row 14:** a drive end held 4–12 s only in memory. It is lost on reload, and `pendingTurnoverHeldMs` is written but read nowhere.
- **Row 15:** the Q3 law is one-shot and latches before its force succeeds.
- **Row 17:** a V366 LIVE refusal drops the write with no retry, and appliers stamp `lastOpponentOutcomeApplyMs` after writing `waiting = false`.
